# System QA Report

Date: 2026-08-19

## Scope and method

Reviewed authentication, role navigation, dashboards, tenants, people onboarding and classes, attendance, Available Systems, profile management, scheduling, shared tables/forms/dialogs, backend validation, Docker Compose, and Nginx configuration.

The review combined source-level interaction analysis, live container health and gateway-log inspection, frontend/backend linting, builds, tests, architecture checks, and responsive CSS review. Authenticated visual browser automation could not be completed because the browser-control connection was unavailable, so viewport observations below are code-backed risks rather than screenshot-confirmed defects.

## Fixed during QA

### Expired sessions remained in the UI

Expired or malformed persisted JWTs are now removed before the application renders. Active sessions are logged out when the token expires, when an authenticated API request returns `401`, when an idle tab becomes visible after expiry, and when another browser tab logs out. Automatic logout now explains why the user returned to login.

### Gateway reported unhealthy while serving traffic

The Docker health check used `localhost`, which resolved to an address Nginx was not listening on in the container. It now targets `127.0.0.1` explicitly.

### Architecture checks depended on the current directory

The architecture guard now resolves the repository from its own script location, so frontend, backend, root, and CI invocations behave consistently.

## Priority findings

### 1. User friendliness

**High: Attendance no longer provides the previously defined workflow.** The page combines recording and history, has no Record Attendance/Daily Attendance tabs, no class/group preselection, and no Today action. Restore those workflows while retaining audience-specific availability and already-recorded indicators.

**High: Bulk onboarding silently reuses controls from Single onboarding.** Bulk role and class are taken from state controlled in another card. A user can submit hundreds of accounts with an unintended role or class. Give Bulk onboarding its own visible role and class controls, plus a pre-submit summary showing count, role, and destination class.

**Medium: Public member registration conflicts with the administrator-led onboarding model.** The login screen still exposes “Create member account” and requires users to know a tenant slug. Confirm whether self-registration is an intended tenant-configurable capability. Otherwise remove it from login and keep first-login onboarding as the sole member entry path.

**Medium: Success and error feedback is easy to miss.** Page-level chips persist without dismissal and actions inside confirmation dialogs surface errors only inside the dialog. Standardize dismissible toasts for completion and retain inline field errors for corrective action.

### 2. User experience

**High: Unsaved-change protection is inconsistent.** User and class editors protect dirty data, but tenant, profile, Available Systems, and several scheduling editors can close or navigate away without the required discard confirmation. Introduce one reusable dirty-form controller and route-blocking policy.

**High: Attendance submission is not atomic.** The frontend sends one request per selected person with `Promise.all`. A network or validation failure can leave a partially saved set while the dialog reports failure. Add a transactional bulk-attendance endpoint returning created, unchanged, and failed records.

**Medium: Large forms lack progressive disclosure.** Tenant registration and profile/system settings present many fields with little grouping or supporting context. Group terminology, identifiers, localization, administrator details, and systems into named sections with concise summaries.

**Medium: Long-running data loads have inconsistent states.** Tenants has a loading state, while attendance, people, profile, systems, and scheduling often render empty content before requests settle. Use shared loading, empty, retry, and stale-data states across every data page.

### 3. Ease of use

**Medium: Tables paginate only in memory.** Every page downloads all records and then searches/paginates locally. Move common table queries to server-side `search`, `page`, `pageSize`, sorting, and total-count contracts before tenant datasets grow.

**Medium: Pagination does not support direct navigation.** The control only offers Previous/Next and displays the current page as text. Add first/last and nearby page choices for large result sets.

**Medium: Schedule setup is clearer but still depends on repeated modal work.** Add contextual “create and select” actions from session and week-template selectors, while preserving the three-step setup model.

### 4. Validation

**High: Native field constraints are not consistently executed.** Most save actions are buttons that open confirmation dialogs rather than form submissions. Attributes such as `required`, `type="email"`, and `minLength` therefore do not prevent invalid saves. Build a shared HeroUI form layer with schema-based client validation that mirrors backend Zod constraints and places errors beside fields.

**High: Tenant administrator details are all-or-nothing but the UI does not explain this.** Entering only an administrator display name sends the entire incomplete administrator object and fails at the API. Add an explicit “Create initial administrator” switch and validate all required fields when enabled.

**Medium: Client-side limits do not mirror backend limits.** Notes, descriptions, names, duration, and schedule ranges generally lack visible maximums or early validation. Export shared constraints or generate them from the API schema to prevent avoidable round trips.

**Medium: Date inputs are inconsistent.** Scheduling and attendance use native string date fields in several places despite HeroUI calendar/date-picker usage being an established requirement. Standardize date parsing, display, min/max rules, timezone behavior, and range validation.

### 5. Mobile friendliness

**High: Mobile navigation consumes document space instead of behaving as an app drawer.** The sidebar becomes a top block and can occupy up to 60% of the viewport. Replace it with a HeroUI drawer/sheet opened from the top bar, with focus trapping and an explicit close action.

**Medium: Operational tables depend on horizontal scrolling.** Keep tables for larger viewports, but use prioritized columns and a compact row-detail/action pattern below tablet widths.

**Medium: Dense schedule grids are only partially adapted.** Week-template and calendar layouts need touch-target, overflow, sticky-label, and small-screen interaction testing at 320, 375, 768, and 1024 pixel widths.

## Operational and test gaps

- The production frontend bundle is approximately 1.16 MB minified (342 KB gzip). Route-level lazy loading should split scheduling, systems, tenant, and people features.
- Database integration tests exist but two are skipped by the default test command. Run them against an isolated MySQL service in CI.
- Add component tests for dirty-form dismissal, multiselect behavior, table search/pagination, duplicate-submit prevention, and automatic logout after authenticated `401` responses.
- Add end-to-end tests for each role's primary journey and mobile viewport checks before release.

## Recommended implementation order

1. Restore and transactionally harden Attendance, including class selection and Daily Attendance.
2. Separate Bulk onboarding controls and add a review summary.
3. Introduce shared schema-backed forms and dirty-form navigation protection.
4. Convert mobile navigation to a drawer and define compact table behavior.
5. Add server-side table contracts, route-level code splitting, and end-to-end role tests.

## Remediation completed

The following changes were completed after the initial review:

- Rebuilt Attendance into separate Record Attendance and Daily Attendance workflows with audience, date, class, search, per-person status, existing-record visibility, and Today controls.
- Replaced per-person attendance requests with one validated, transactional batch endpoint. Duplicate or invalid rosters roll back as a unit.
- Added independent Bulk onboarding role/class controls, a pre-submit summary, uppercase identifier normalization, 1,000-row limits, and client-side schema validation.
- Removed public member self-registration from login so administrator onboarding and first login are the single account-entry workflow.
- Replaced persistent feedback chips with dismissible HeroUI alerts while keeping corrective errors beside fields.
- Added shared schema-backed fields and Zod validation to onboarding, tenant registration/editing, profile, and Available Systems settings.
- Added explicit initial-administrator opt-in and conditional validation during tenant registration.
- Added dirty-state protection to tenant, profile, Available Systems, people, classes, and scheduling editors. Scheduling modals cannot be dismissed through the backdrop, only changed forms require discard confirmation, and app navigation/sign-out uses one shared unsaved-change guard.
- Standardized Attendance, Regatta, schedule calendar, and schedule editor dates on the HeroUI date picker.
- Added loading/retry states to operational pages touched in this pass.
- Replaced the mobile sidebar block with a focus-managed HeroUI drawer.
- Added compact mobile table rows, direct page navigation, first/last controls, search, and 10/25/50 page sizing.
- Added route-level lazy loading for large feature pages.
- Updated vulnerable frontend transitive dependencies; `npm audit fix` reported zero known vulnerabilities at completion.
- Added malformed/expired JWT rejection, scheduled expiry logout, cross-tab logout synchronization, authenticated `401` logout, and a visible expiry reason.

## Remaining release gates

These are larger delivery tracks rather than unresolved interaction defects from the reviewed screens:

- Introduce server-side query contracts for high-volume people, tenant, and historical attendance tables before a tenant exceeds the current bounded operational dataset. The shared table already supplies the target search and pagination interaction.
- Add isolated MySQL integration execution to CI; two integration tests remain opt-in in the local test command.
- Add browser end-to-end journeys for all four roles and screenshot checks at 320, 375, 768, and 1024 pixels. Source, lint, build, and unit checks pass, but the browser-control connection was unavailable for this review.
- Continue reducing the 226.61 KB gzip initial shared HeroUI shell chunk. Feature routes are now split, with Scheduling loading as an 11.12 KB gzip feature chunk.
